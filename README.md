# mongo-freshness

Client-observed replica freshness measurement for MongoDB replica sets.

Method follows Wada, Fekete, Zhao, Lee and Liu, *Data Consistency Properties and
the Trade-offs in Commercial Cloud Storages: the Consumers' Perspective*,
CIDR 2011. The central artefact is their Figure 2: the probability that a read
returns the freshest value, as a function of time elapsed since the write.

## Install

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

Requires a running replica set. The default config assumes `rs0` on
`localhost:27017-27020`.

## Run

```bash
python -m harness.collect --config config/baseline.yaml --calibrate
python -m harness.analyse measurements/<run_id>
```

`--calibrate` first measures client-side read round-trip against a value that
cannot be stale. Anything below that p50 is under the harness's resolution and
should not be interpreted.

## Run directory layout

One directory per measurement, named `<UTC timestamp>__<experiment name>`.

```
measurements/20260908T143000Z__baseline/
├── config.yaml                 verbatim copy of the config that produced this
├── manifest.json               run id, clock anchor, resolved config, file index
├── writes.jsonl.gz             one record per write
├── reads.jsonl.gz              one record per read
├── repl_samples.jsonl.gz       replSetGetStatus at each cycle boundary
├── checksums.txt               sha256 of every file above
├── provenance/
│   ├── client_env.json         python, pymongo, OS, CPU, power source, clock sync
│   ├── git.json                commit hash + whether the tree was dirty
│   ├── nodes.json              per-mongod buildInfo, hostInfo, getCmdLineOpts, FCV
│   ├── repl_before.json        rs.conf() + rs.status() + hello, before the run
│   ├── repl_after.json         same, after
│   ├── server_status_*.json    trimmed serverStatus before/after
│   └── calibration.json        client-side read overhead distribution
└── derived/                    regenerated by analyse.py, gitignored
```

Raw files are committed; `derived/` is not. If a run's raw data exceeds what is
comfortable for git, use git-lfs rather than trimming the record.

## Data schema

### `writes.jsonl`

| field | meaning |
|---|---|
| `cycle` | cycle index, also the value written into the document |
| `seq` | sequence number written (equals `cycle`) |
| `t_start_ns` | perf_counter_ns immediately before the command is issued |
| `t_ack_ns` | perf_counter_ns immediately after acknowledgement returns |
| `latency_ns` | `t_ack_ns - t_start_ns` |
| `operationTime` | cluster time `{t, i}` from the server reply |
| `primary` | host:port of the primary at this cycle, from `hello` |
| `write_concern` | the write concern document actually sent |
| `ok`, `n`, `nModified`, `writeConcernError`, `error` | outcome |
| `warmup` | true if this cycle is discarded in analysis |

### `reads.jsonl`

| field | meaning |
|---|---|
| `target` | read path id, defined in config `targets` |
| `cycle`, `sweep` | which write-then-poll cycle, and which sweep within it |
| `t_start_ns` / `t_end_ns` | perf_counter_ns around the read |
| `latency_ns` | round-trip |
| `observed_seq` | sequence number in the returned document, or null |
| `observed_wall_ns` | wall clock stamped into the document by the writer |
| `operationTime` | cluster time from the reply |
| `error`, `warmup` | as above |

Note what is **not** here: no `fresh` column, no bucket, no staleness. Freshness
is a derived judgement and lives in `analyse.py`, so that changing the
definition never requires re-collecting.

### Clock

All `*_ns` values come from `time.perf_counter_ns()` in one client process, so
they share a single monotonic clock and carry no inter-host skew. `manifest.json`
records an anchor pair mapping that clock to wall time. This is a real advantage
over the CIDR setup, where writer and reader were separate EC2 instances, and it
disappears the moment measurement moves to Atlas or multiple client hosts.

## Derived outputs

| file | contents |
|---|---|
| `curve_ack.csv`, `curve_start.csv` | P(fresh) per target per time bucket, with Wilson 95% CI and sample count |
| `headline_*.csv` | per-target scalars: overall P(fresh), first bucket at P≥0.99, last bucket at P<1.0 |
| `monotonic_reads.csv` | consecutive-read regressions per target (analogue of CIDR Table 2) |
| `lag_writes.csv` | distribution of how many writes behind each target was |
| `freshness_curve_*.png` | the Figure 2 analogue |

Two elapsed-time anchors are computed for every curve: `start` measures from
write submission, `ack` from write acknowledgement. CIDR uses both (Table 1 uses
write start, Figure 2 uses write completion) and they answer different
questions, so neither is baked into collection.

## Experiment naming

One config file per experimental condition, one run directory per execution.
Never edit a config to change a condition; copy it. The config file in the run
directory is the ground truth for what was measured.
